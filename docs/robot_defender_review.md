# Robot-Defender 重力与固件参考核验

输入为用户提供的 `Robot-Defender.zip`，ZIP注释为 `176d4c502478387f1b63206402a1fc0821531db2`。它是参考包身份线索，不能据此证明实物当前烧录的版本。完整文件和视频保存在 `references/robot_defender/`，哈希见同目录 `manifest.json`。该快照只读，没有运行其中的板级任务、CAN发送、UDP bridge、构建刷机或电机使能。

用户陈述该代码已在实物验证重力补偿。视频可解码，约18.49 s、1280×720、约29.97 fps；检查的5 s画面可见手动接触机械臂。视频没有本项目可读取的逐轴位置/力矩、固件哈希和测试工况，故只记录为用户提供的实物示范证据，不推导定量补偿精度。

## 可直接借鉴的内容

`zephyr_app/src/model/arm_gravity/src/arm_gravity.cpp` 有独立的六轴 URDF 重力计算接口；`arm_gravity_fitted_model.h` 含6轴运动链、固定工具变换和拟合参数。可只编译这一个纯计算翻译单元，不依赖STM32、Zephyr或七轴IK。

本项目新增 `tests/fixtures/defender_gravity_host.cpp`：从标准输入读取世界向上方向与6关节角，调用原版六轴C++重力代码，输出6力矩。它没有硬件传输入口。`tools/defender_parity.py` 用独立URDF势能差分和本项目MuJoCo重力交叉验证：

```bash
rtk proxy .venv/bin/python -I tools/defender_parity.py --samples 128 --output reports/defender_parity.json
rtk proxy .venv/bin/python -I -m pytest tests/test_defender_reference.py
```

需要宿主 `g++` 和已恢复的参考快照。未导入参考时这组可选测试显示跳过；第一阶段交付机器已实际编译并运行，无跳过。

128组独立随机构型/重力方向（含倾斜和倒置），以及包内256组CSV对照：

| 比较 | 最大绝对差 |
|---|---:|
| 原版C++与包内CSV | 约1.36e-6 N·m |
| 原版C++与原始URDF势能差分 | 约1.45e-6 N·m |
| 去重URDF势能差分与当前MuJoCo | 约1.76e-9 N·m |
| 原版拟合C++与去重模型 | 约0.15135 N·m |

最后一项是预期模型差异：旧拟合参数目标包含原CAD的重复末端质量。本项目去重后不能照搬旧参数或“拟合已通过”的结论。重力回归公式与运动链有复用价值，质量/质心先验须随新模型重建；本阶段没有把旧拟合参数写入实物。

## 代码中实际存在的电机映射

参考 `zephyr_app/src/application/inc/config.h` 和 `src/application/src/arm_task.cpp`：

```text
q_urdf[i] = direction[i] * (q_motor[i] - zero_offset[i])
tau_motor[i] = direction[i] * tau_urdf[i]
direction = [1, -1, 1, 1, 1, 1]
zero_offset = [0.015, -0.027, 2.526, 1.348, -2.493, 0.412]
```

这些是包内程序的明确配置，不能说“没有映射”，也不能未经证据就说非零零偏是占位值。但它们是否对应用户当前机械结构、当前编码器零点与视频版本，仍未独立确认。新项目保留URDF原生关节角作为仿真接口，硬件未知配置继续为 `null`。

参考程序配置的关节力矩限幅为 `[4,4,3,2,1,1]`，并有20 ms反馈新鲜度检查。这只能证明软件设了这些限制，不能证明它们是电机额定能力或完整的实物保护策略。`kArmUpBase=[0,0,1]` 固定正立；算法支持其他重力方向，不等于板级任务已实时使用IMU倾角。

`config.h` 默认定义 `GIMBAL`，`CUSTOM_CONTROLLER` 被注释。`arm_task.cpp` 的保持任务明确计算关节刚度/阻尼加重力，再作限幅。另有自定义控制器任务路径；必须核对用户实物使用的编译角色和入口，不能把当前ZIP默认角色直接说成视频里的纯重力模式。

## 力矩反馈仍需核实

`zephyr_app/src/devices/motor_synthesis/` 中达妙MIT报文发送和反馈使用同一组 `T_MIN/T_MAX` 做12位数值映射，定义是 ±7，反馈行旧注释写 ±10。文档/注释与实际宏不一致，应以当前编译定义为软件行为证据。

这不足以确定数值在目标DM4310固件上的物理意义。当前路径没有足够证据确认减速比或力矩常数换算，无法判断反馈代表电机侧/输出侧力矩、电流换算值还是其他定义。因此±7、软件逐轴限幅和本项目数值限幅±10分别记录；三者均不写成DM4310的额定能力。

用户确认现物为达妙4310，优先记录该事实；不能从另一CAD文件名推断实际六轴混用电机。真实反馈也不直接等于末端外力：还需处理重力、摩擦、惯性、传动效率及Jacobian可观性。

## 对 Claude 输出的独立复核

Opus提供了协议/重力审查和宿主harness/测试草稿。最终harness按真实API修正，并由独立URDF势能和MuJoCo对照运行。它提出的以下说法未采用：

- 根据旧文档声称没有CAN/关节映射；实际配置和任务代码已存在映射。
- 将非零零偏一概判作占位值；代码存在配置，是否标定需追溯，不能猜。
- 推断六轴实际混用电机；与用户确认冲突且没有铭牌证据。
- 说重力对照没有覆盖倒置方向；本项目球面采样与实际参数支持负z方向。
- 把正确的固定关节质量折叠等同于算法重复计数；本案重复源于CAD输入已有两份同实例，需从源模型删除一份。

有效的优化已落实为：六轴纯计算模块的离线对照、输入严格校验、原始/去重模型结果分列、旧协议注释冲突记录、映射来源与未验证项拆开。没有因此修改参考快照、迁移七轴IK或运行实物控制。
